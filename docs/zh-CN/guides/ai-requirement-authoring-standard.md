# Brain Creator AI 需求文档编写标准

本文说明如何编写适合 Brain Creator 分析、审核、编译、执行和复核的需求文档。标准来自招聘/Offer 正式需求包的结构复盘，也遵循 Brain Creator 的来源追踪、流程建模和证据门禁。

## 核心要求

- 每条业务规则都有稳定编号、明确适用范围和来源锚点；表格、子文档、图片和流程图也属于来源。
- 业务预期、目标系统当前行为和一次运行结果分开记录。系统现状不能自动改写业务要求。
- 流程写清参与角色、前置状态、触发动作、分支条件、目标状态、业务副作用和可观察结果。
- 不确定、冲突和缺失项公开列出，由业务负责人确认；AI 不猜路径、字段含义、权限或预期值。
- 测试断言对应明确的业务后置条件；“页面显示成功”、截图路径或自动化通过本身不等于业务符合。
- 数据创建、复用、转交、清理或保留均说明责任和边界。可能重复写入时写明幂等键或恢复核对方式。

## 正式需求样本复盘

本标准由一份已标记正式发布的招聘与 Offer 需求包反推。复盘只提炼文档质量规则；样本业务规则不能直接复用到其他系统或项目。

样本显示，正文、字段工作簿、状态图、流程图和评论共同构成需求来源。主文档的“字段见表格”不能视为字段规则已经齐备；工作簿应逐个列出并读取所有相关工作表。样本中的主文档虽标记正式发布，版本字段仍写“待定”，因此不能只用文档状态或人类可读版本号作 Trial（试验轮次）身份；应同时保存源 revision、全部子资源 revision 与哈希。业务负责人声明当前内容为正式版时，可按其声明使用，但必须把未填写的版本字段作为来源元数据记录。

| 样本中观察到的写法 | 对 Brain Creator 的风险 | 编写和分析要求 |
|---|---|---|
| 正文通过“字段见表格”引用多个工作簿；其中还有空白工作表 | 只导入正文会漏掉字段条件；把空白工作表当作“没有遗漏”也没有证据 | 列出引用的全部子资源和工作表，记录读取范围、revision、哈希及空表状态；字段条款绑定到实际工作表和行 |
| 个别字段的数据来源以问号收尾 | AI 可能把猜测变成数据绑定或测试断言 | 保留为待澄清项，指定责任人；不从相邻字段或系统现状推断来源 |
| 正式员工与实习生表格结构相似，但重聘字段用语、回填和编辑行为有差别 | 合并表格会抹去适用条件和真实差异 | 按用工形式拆分适用矩阵；相似字段可登记候选别名，未经确认不得合并规则 |
| 表格把必填、显示、隐藏、清空、默认值、可编辑和校验写在同一个单元格 | 仅提取“必填”会漏掉条件改变后的清空或状态副作用 | 把每个字段展开为条件、默认、读写、校验、联动和清空规则；保留原始单元格及行号 |
| 联动规则引用一个条件字段，但该字段没有出现在当前字段表的字段列 | AI 可能凭条件句虚构可填写的控制项或默认值 | 先交叉检查正文、子表和字典；若业务负责人补充字段触发/呈现规则，记录为单独确认来源。其值、类型或可编辑性仍未知时继续保留对应 Gap，不生成推断值或断言 |
| 流程图并列业务提供路线与系统配置路线 | 把两图拼成一条路径会制造并不存在的审批链 | 先指定业务预期来源；把目标系统路线作为独立观察，后续核对差异，不以配置覆盖需求 |
| 评论提出流程状态问题，并回复“已调整” | 评论解决意图不证明当前正文或附件已同步 | 读取评论与指定 revision；核对修改后的正文/附件锚点，仍有差异就保留 Gap（待处理项） |
| 状态转换同时更新 Offer、本地审批记录和外部系统数据 | 只断言页面状态会遗漏跨对象副作用、失败与补偿 | 为每个转换列出对象变化、接口/回调、失败语义、重试与独立查询证据；未授权的外部副作用不得执行 |

样本复盘体现了一个基本区分：文档“正式发布”、某个字段“写得明确”、系统“观察到这样”是三种不同事实。AI 应分别记录来源状态、规则完整度和系统证据，不把其中一种替代另外两种。

本次复合来源样本中，字段表的显隐规则引用了未在字段名列定义的条件项。业务负责人于 2026-10-30 确认：选择“实习生”用工形式时，前端会带出“是否占编”字段。应将其作为有来源的用户补充记录；该字段的实际值、控件类型、是否可编辑及提交后的落库位置仍要通过目标系统观察或补充需求确认，不能由“带出”一词推断。

## 推荐文档结构

| 章节 | 必须写清 | Brain Creator 中的用途 |
|---|---|---|
| 文档控制 | 需求编号、版本、状态、负责人、更新时间、评审人、适用系统和生效日期 | 冻结 RequirementSet（需求集）及 Trial（试验轮次）来源 |
| 背景、目标与非目标 | 当前问题、业务目标、明确排除事项及成功标准 | 区分背景陈述与可测试条款 |
| 部署和业务范围 | 系统/租户、组织根、地区、员工/对象类型、内外部系统边界 | 建立系统适用矩阵，阻止跨部署误套规则 |
| 角色和权限 | 角色定义、组织/数据范围、可执行动作、禁止动作、委托规则 | 生成角色交接、权限和越权覆盖 |
| 业务对象和数据 | 对象关系、唯一性、必填、类型、默认值、校验、可编辑性、显示条件、数据来源 | 建立业务实体、字段规则及 TestDataProfile（测试数据档案） |
| 业务流程 | 主路径、可选路径、角色、条件、跳过/并行/回退、跨系统调用 | 建立 WorkflowModel（流程模型）和路径覆盖 |
| 状态和转换 | 初始/中间/终止状态、转换触发者、条件、失败状态、恢复/撤回规则 | 建立 StateMachineModel（状态机模型）及正反向转换 |
| 集成和副作用 | 来源/目标系统、请求/回调、字段映射、失败处理、重试、补偿、幂等、授权边界 | 区分本地场景与外部依赖；标记不可执行写入 |
| 异常与安全 | 重复提交、无权限、数据冲突、失效登录、超时、并发、审计、敏感信息 | 生成负向场景、恢复和安全验证 |
| 非功能要求 | 指标、单位、起止点、测量条件、样本量、环境和阈值 | 避免把“快/稳定/兼容”转成无依据断言 |
| 验收条件 | Given/When/Then（前置/动作/结果）、实际可观察字段、适用条件和证据来源 | 生成 TestIntent（测试意图）、断言合同与 Oracle（业务预期） |
| 测试数据和清理 | 合成/真实数据、依赖、复用条件、标识、清理/保留策略、失败后处置 | 规划数据生命周期和写入恢复 |
| 附件与引用 | 子文档、表格所有工作表、图片、白板、版本、哈希、区块/行/边引用 | 保障解析完整、来源保真和可重评估 |

## 原子业务条款格式

一条条款只表达一个可判断的业务规则。建议使用下表，字段可按业务裁剪，但来源、适用条件和结果不可省略。

| 字段 | 写法 |
|---|---|
| 条款编号 | 稳定且唯一，例如 `REQ-OFFER-STATE-004`；修订时保留编号并记录版本差异 |
| 来源 | 文档版本、章节/区块 ID、Sheet/工作表及行号，或图片/白板 ID 与节点/边 ID |
| 适用条件 | 系统部署、组织根、角色、对象类型、当前状态、字段值等明确谓词 |
| 前置状态 | 执行前必须成立的对象状态、数据关系和授权 |
| 角色与动作 | 谁通过哪个业务动作执行什么操作 |
| 预期结果 | 字段值、状态转换、对象新增/更新、关联对象副作用或“无变化” |
| 失败/取消结果 | 阻止、提示、回退、重试、补偿和是否允许再次提交 |
| 外部副作用 | 外部系统、调用/回调、字段映射、超时/失败与授权边界；没有副作用时明确写“无” |
| 证据 | 可独立读取的页面字段、列表状态、业务记录或外部回执 |
| 确认状态 | 已确认、草稿、待澄清、存在冲突；说明确认人和时间 |

验收句式：

```text
Given <适用条件与前置状态>
When <角色执行的动作>
Then <可观察的业务结果>
And <关联副作用或明确无副作用>
```

不要把一个包含多个分支的流程压进一条“端到端正常”用例。应按每条状态转换、关键角色交接和业务副作用建立可追踪的条款，再聚合成场景。

### AI 分析的固定输出

每次需求分析至少交付以下五类记录，并保留类别边界：

1. **来源事实**：带稳定来源锚点的原文或忠实转录，不加业务解释。
2. **规则条款**：原子化的显式规则，标注适用条件、确认状态和来源。
3. **推导候选**：由多条来源组合得出的候选场景或映射，写出推导步骤和置信度，等待审核。
4. **系统观察**：目标系统上的页面、字段、角色、路由、状态和观察时间，不能改写需求条款。
5. **待澄清/冲突**：缺失条件、术语冲突、附件歧义、权限未知、外部依赖和处理责任人。

Coverage Critic（覆盖审查器）要逐项检查字段、业务对象、流程路径、角色交接、状态终态、分支、异常、外部副作用和可观察 Oracle（业务判定依据）。如果没有证据支持默认行为，应标记未知，不得将“未写”解释为“允许”“不影响”或“无副作用”。

生成测试意图时还要通过以下质量检查：

- 每条意图应对应明确的业务行为或用户确认的 outcome（验收结果），并保留稳定 ID 与来源锚点；不能只按文档章节或主题机械生成一条宽泛意图。
- 前置条件描述该业务场景所需的对象、状态、角色、关系和条件。`RequirementSet 已批准`、`目标环境可用` 等全局准入条件单独记录为执行门禁，不能充当场景前置条件。
- 预期结果写成可观察的字段值、状态变化、关联对象副作用或明确的无变化；不得直接复制 objective（测试目标）或需求原句后就视为可执行 Oracle。
- 核对意图到固定 outcome 的关联数量和唯一性。没有显式关联的 outcome 仍是未覆盖；意图总数、来源可追踪率和主题命中数都不能替代业务路径覆盖。
- 对每条意图检查适用系统、组织根、角色、数据准备与独立后置证据。无法确认时保留草稿/阻塞状态，不用通用模板补齐。

## 流程、状态和分支的写法

状态转换至少列出：来源状态、动作、执行角色、条件、目标状态、相关对象变化、外部调用、失败结果和证据。分支条件使用明确比较关系，例如 `amount >= 10000`；避免“较大金额”“特殊部门”等不可执行描述。

每张流程图必须附可检索的文字化节点和边。图中每条边写明条件、角色和来源。不同图表示不同部署、角色或流程版本时，要分别命名并说明适用范围；若相互冲突，建立待确认项，不让 AI 选择其一。

### 条款示例：关闭业务对象

```text
REQ-OBJECT-CLOSE-001
适用条件：执行者具有关闭权限，主对象当前处于可关闭状态。
前置条件：读取主对象关联记录及其当前状态。
规则：关联记录处于明确的阻止状态时，关闭操作被拒绝，并指出阻止项。
规则：不存在阻止状态但存在待处理关联记录时，显示二次确认。
确认后：主对象进入需求定义的终态；需废弃的关联记录按条款进入对应终态。
取消后：提示关闭，主对象和关联记录均保持原状态。
证据：分别读取主对象和关联记录的列表/详情及流程历史。
外部副作用：关联流程的取消需单独说明系统边界、回执和失败处理；未定义时不得推断。
```

如果正式文档正文、附件或系统当前配置相互矛盾，应保留三方证据和差异，不用“系统目前就是这样”代替业务确认。

## 字段表和测试数据

字段表应逐字段说明：业务名/稳定 ID、对象、类型、必填条件、默认值、选项来源、校验/边界、格式、联动显示和清空规则、读写权限、数据来源、脱敏要求及提交后可查询位置。表单的“显示/隐藏”不代替必填和清空规则；字段类型也不代替业务语义。

测试数据档案应说明唯一匹配条件、多匹配处理、是否创建、创建后核验、跨场景实体引用和清理方式。不得用现有员工或业务数据代替合成夹具。允许保留的数据应带测试标签，并标出负责人及保留期限。

## 附件、子文档和版本冻结

- 导入前列出完整 Wiki/文档层级、子文档、表格所有工作表、白板和媒体；有未读取节点时标记源包不完整。
- 记录每个资源的 revision、稳定资源 ID、标题、内容哈希和读取时间；Trial 的内容哈希应覆盖全部子资源和附件。
- 将图片/流程图保留为原始附件并附文字化节点/边。OCR/AI 转录只作为候选，必须保留置信度、坐标/来源和人工确认状态。
- 图片重复、模糊、截断或没有可读的预期值时显式标注。不能仅凭图片文件名、alt 文本或缩略图断言它已被完整分析。
- 旧版本可以查看和重评估，但不能用来填充新 Trial 的结果。

## 与 Brain Creator 的工作流

1. 导入来源并固定 revision、子资源和内容哈希。
2. 逐个分析表格、图片、流程图和白板；确认与拒绝的解读均留下记录。
3. 将背景、明确条款、推导候选、系统观察和待澄清项分开。
4. 运行覆盖审查，核对字段、流程、状态、权限、集成五个维度，以及主路径、转换、角色交接、异常分支和终止状态。
5. 由业务负责人处理冲突和不完整的 Oracle；未决项保持 Draft（草稿）/blocked（受阻），不得批准基线。
6. 生成测试设计；每个 TestIntent 都引用需求条款/已确认附件边，并绑定适用条件、数据方案和可观察后置条件。
7. 从已审核的需求章节和选定场景生成探索工作包，限定系统入口、路由、角色、业务对象、只读动作、禁止动作及未覆盖项。章节只用于划分探索范围，不能自动变成已观察页面或可执行步骤。
8. System Brain（系统大脑）只记录目标系统实际观察到的页面、导航、角色、控件、状态、快照和证据。安全探索沉淀版本化 PageModel（页面模型）、LocatorPoint（定位点）、导航边和状态观察；写入型流程必须另走已批准的探索/执行计划。流程设计器截图按可见范围记录节点和条件；若画布被裁切或没有显示流程 ID/版本，应明确标为局部观察，不能据此确认完整流程或版本绑定。
9. 页面模型应按页面身份和路由组织；定位点记录语义名称、控件类型、唯一定位方式、来源观察与快照版本。字段名相同但页面、角色或部署不同，应保持不同绑定；不得仅按需求表格中的字段名拼出定位器。
10. 确认 System Brain 快照后，知识驱动 POM（页面对象模型）才能按 `pageModelId` 与 `locatorPointId` 操作当前页面，并记录快照、路由、定位点、动作和结果。路由不匹配、定位缺失、匹配多个元素或控件不可见时，停止并要求重新探索；不得静默改用备用选择器。
11. POM 只解决“如何找到并操作页面”。流程顺序、角色交接、业务实体、写入确认、断言和 Oracle 由需求、用例、Harness（任务编排运行时）和验证合同决定。复杂控件使用明确登记的扩展；目标系统专用扩展留在业务验收资产中。
12. 批准需求基线后，冻结需求哈希、系统快照、代码/运行版本、授权范围及场景分母，再启动 Trial。

### 从需求章节派生探索范围

需求章节用于整理覆盖，不直接等于页面模型。每个探索工作包应把业务需求、预期证据和目标系统观察一一对应，并记录未能观察的部分。

| 需求内容 | 探索范围候选 | 可沉淀的 POM 页面知识 | 边界 |
|---|---|---|---|
| 业务范围、部署和角色 | 登录后入口、菜单、组织/部署选择、角色可见页面 | 路由、页面身份、角色可见性和导航边 | 不根据文档推定登录账号实际角色；不修改权限配置 |
| 对象字段和表单 | 列表入口、表单分区、详情和只读字段 | 页面级 `PageModel`，字段/按钮/提示的 `LocatorPoint` | 字段规则仍来自需求；仅观察控件不能证明必填、默认值或保存结果 |
| 查询条件与列表 | 列表路由、查询控件、结果表格、详情入口 | 查询/列表/详情页面模型及导航关系 | 查询结果应保留筛选条件和数据范围；不得把空结果推断成无业务数据 |
| 流程和状态转换 | 任务列表、业务详情、审批记录、状态操作入口 | 角色对应的页面模型、定位点和观察到的状态边 | 安全探索只读；提交、转交、审批、关闭等写入须由单独批准计划执行 |
| 条件字段和对象类型 | 在不提交数据的前提下查看可用选项和联动 | 观察到的控件类型、选项及条件显隐 | 不得提交临时值触发业务；缺少前置数据时登记探索任务 |
| 外部集成和权限 | 可见的同步标记、回调结果、越权提示或外链 | 只记录目标系统可观察到的路由、字段和提示 | 外部系统写入、清理或权限变更均不由页面探索隐式授权 |

工作包完成后，应复核所有新增定位点的页面归属、唯一性、可见性、来源截图/交互记录和快照版本，再确认 System Brain Snapshot（系统大脑快照）。测试用例只能绑定已确认快照中的页面与定位点。

招聘、Offer 或其他有多个对象类型的需求，至少把每种表单、列表、详情和角色入口分别作为探索切片。若不同用工形式、部署、组织根或角色可能显示不同页面，应通过页面路由和实际观察确认是否共用 PageModel；不得因文档结构相似就复用同一个页面对象。
