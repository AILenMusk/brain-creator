## 1. 验收目标

本阶段的首要工作是对已经实施的 A–F 内容逐项验收，确认实现是否满足已批准的交付条件。先审代码和已有证据，再补跑缺少的验收项；不以新增功能、代码存在或合成用例通过代替验收。

每项结论都要能回答：验收了哪个行为、对应什么实现、用什么反例证明门禁有效、在哪个准确版本运行、结果和产物在哪里。

真实业务 Trial 是业务闭环验收的一部分，不是 A–D、F 等通用工程实现验收的前置条件。没有真实 Trial 时，工程实现仍可独立验收；真实业务指标必须标为未测量。

## 2. 三类结论分开报告

| 结论 | 判定对象 | 计数规则 |
|---|---|---|
| 候选实现验收 | 当前候选 commit 中 A–F 各包的代码行为及工程证据 | 单独报告候选通过数，例如 4/6；不代表已进入基线 |
| 正式交付完成度 | 已合入选定基线且完成合入后冒烟的交付包 | 按原定口径报告 N/6；未合入候选不得计入 |
| 真实业务完成度 | 冻结范围内，由独立目标系统后置状态证明通过的真实场景 | 通过场景数 / 冻结场景总数；blocked、失败、未执行均留在分母 |

自主完成度使用同一冻结场景分母，报告无需额外人工操作且真实通过的场景数 / 场景总数。初次授权和登录单列；后续人工介入逐次记录原因、步骤及是否可恢复。

合成夹具、mock、历史截图和代码内模拟数据只证明工程行为，不计入真实业务完成度、自主完成度、真实恢复率或业务准确率。无真实样本时指标写“未测量”，不写 0%、通过或估算值。

## 4. 结论等级

| 状态 | 判定标准 |
|---|---|
| 通过 | 包内每项强制验收条款均有准确版本的实现证据、正向结果、失败反例和必需集成/宿主证据 |
| 部分通过 | 实现和部分验收证据成立，但仍有包内强制门槛未完成 |
| 未通过 | 出现违反验收条款的行为，或失败反例仍能得到错误成功 |
| 阻塞 | 缺少目标系统、权限、鉴权、数据 Provider、独立查询等外部前置 |
| 未测量 | 没有符合口径的运行样本，不能得出指标结论 |
| 未执行 | 计划内的验收动作尚未运行；不得写成通过 |

“候选实现通过”与“正式交付通过”必须分栏记录。代码未合入时可以先完成候选实现验收，但正式 N/6 仍按基线纳入规则计算。

## 5. 统一验收流程

### 第一步：冻结验收对象

记录基线与候选 SHA、PR 状态、工作区是否干净、版本与锁文件、Store schema、构建身份、MCP PID/启动时间、workspace、Provider。身份字段无法确认时写未知，不得由磁盘源码推断运行进程版本。

### 第二步：逐条映射验收声明

把 A–F 的验收条款拆成可观察的行为，逐条映射到实现文件、入口、数据资产和现有测试。仅有测试文件或 mock 调用、但未验证实际产品行为的，不算通过证据。

### 第三步：先执行失败反例

优先运行能揭露错误成功的反例。反例失败时，对应包不能通过；修复后重跑原反例和受影响回归。不得通过删场景、放宽 Oracle、降低断言强度或跳过写操作来消除失败。

### 第四步：运行功能及集成门禁

先跑相关测试文件和包级检查，再跑完整工程门禁。所有结果绑定同一个候选 SHA。代码或测试变化后，旧 commit 结果不覆盖新 commit。

### 第五步：核对运行入口和交付形态

按受影响范围核查 npm/源码安装、CLI、MCP/Facade、Plugin/Skill、宿主 Agent、浏览器运行、任务恢复、静态报告、包安装与 workspace 隔离。只有配置文件或 CI 工作流而没有实际执行记录，标为未执行。

### 第六步：独立复核与归档

将原始命令、退出码、测试数量、CI 结果、运行身份、失败记录及报告产物归档到本轮台账。复核结论不只引用摘要；复核人应能从 SHA 和证据链接重现判断。

### 第七步：基线纳入后复验

合入后重新核验实际运行身份、新目录安装、CLI/MCP/宿主入口与最小恢复冒烟。通过后该包才计入正式 N/6。npm 发布不属于本次自动动作，必须另行明确授权。

对准确候选 commit 运行并记录：

- 受影响包的失败反例和定向单元/集成检查。
- 全量单元与集成套件、TypeScript 检查和生产构建。
- 文档构建。
- 包内容检查和新目录安装验证。
- 订单浏览器夹具、文档浏览器回归、Host Agent/Codex 原生入口及插件 smoke。
- MCP 运行身份、源码 workspace 隔离、仓库卫生和对应 CI 矩阵。
- 修改涉及恢复、证据或 Conformance 时，补跑其目标系统后置条件、证据真实性和中断反例。

每项记录准确命令、退出码、测试文件/用例数、commit、构建身份、产物路径和是否 synthetic。需要运行真实系统脚本时，先审脚本行为和本轮授权；本策略本身不授权业务写入或清理。

## 8. 真实 Trial 准入门

只有以下条件同时满足，才进入真实业务执行：

1. 需求快照及附件版本、场景名单和固定分母已冻结。
2. 每个场景的前置条件、角色交接、目标状态、条件分支、业务实体和 Oracle 已审核。
3. 当前 Test5 鉴权、路由和角色经过本轮验证；产品授权与用户授权分别记录。
4. 独立目标系统后置查询和 TestData Provider 可用，并绑定正确 systemId 和实体引用。
5. 创建、提交、转交、审批、关闭与数据清理范围符合批准边界；清理前按约定提前通知。
6. 每轮记录 Trial ID、需求/Oracle hash、代码/build 身份、实体引用、操作状态、证据 hash、人工介入及最终清理/保留。
7. 中断恢复先查目标后置状态；已生效操作只对账、不重放。

Test5 的真实场景与 Beisen 场景都不得因为 blocked 或未执行而从冻结分母删除。Beisen 场景在第二真实系统和单独授权到位前保留 blocked。任何需求、Oracle、系统绑定或源码变化都开启新验证记录，不覆盖旧结果。

## 9. 最终验收报告格式

1. 基线 SHA、候选 SHA、PR 状态、运行身份和证据归档位置。
2. A–F 每包的候选结论、正式基线结论、强制条款、正向证据、失败反例、未完成项及复核人。
3. 候选通过数/6 与正式完成度 N/6，明确两者口径。
4. 真实业务、自主完成度的分子、分母和原始场景数；blocked、失败、未执行、人工介入、恢复、清理分别列示。
5. synthetic 证据单列；没有数据的指标标未测量；第二真实系统等外部依赖单独列出。
6. 未通过项的修复 commit 和原失败/复验记录；未授权发布状态。
