## 1. 验收目的与结论口径

验收要分别回答三个问题：候选实现是否正确、能力是否在 Test5 上真实完成业务、在固定场景中有多少场景无需额外人工干预。三个结论分别取证，不能相互替代。

| 指标 | 计算方式 | 当前结论 |
| --- | --- | --- |
| 实现完成度 | 已合入选定基线且满足本策略该包门槛的交付包数 `/ 6` | `0/6`。本地候选提交和合成检查不计入分子。 |
| 真实业务完成度 | 有独立业务后置证据并符合已批准 Oracle 的场景数 `/ 冻结的全部选定场景数` | 未测量。Trial 尚未建立；blocked、失败和未执行场景保留在分母。 |
| 自主完成度 | 无需额外人工操作且真实符合的场景数 `/ 同一冻结场景分母` | 未测量。初始授权/登录单独统计，不隐去后续人工介入。 |

缺数据写“未测量”，不得写成 0%、100% 或通过。实现、真实业务、自主完成三项都必须附样本量、分子、分母、来源 revision、候选/合入 commit 和证据链接。

## 2. 验收证据等级

每个证据记录至少绑定：RequirementSet 与 source revision、`systemId`、`knowledgeProjectId`、代码 commit/build identity、Trial ID、固定场景 ID、合同 ID、步骤 ID、业务实体引用、执行角色、时间、产物实际路径及 SHA-256。缺少绑定的历史产物可以保留和复核，不能靠数组顺序、文件扩展名、标签或旧状态晋升。

| 证据级别 | 内容 | 可支持的结论 |
| --- | --- | --- |
| 需求/设计 | 正式需求、附件分析、人工审核的流程和 Oracle | 只能说明预期与范围，不说明系统已执行。 |
| 候选工程 | 单元、集成、构建、文档、隔离安装和浏览器夹具 | 说明候选代码行为；synthetic 结果只进入 synthetic 指标。 |
| 真实执行 | 本轮 Trial 的步骤记录、运行绑定产物及失败/介入记录 | 说明尝试执行；自身不能证明业务后置状态。 |
| 独立业务 Oracle | 从目标业务列表/详情/API 重新读取的实际状态、实体与关联副作用 | 与合同匹配后，才支持真实场景符合结论。 |

截图、trace 和报告必须从本次执行实际文件读取并验证可解码/可读取、hash 一致、run 与 step 归属一致。目标值变更、断言删除、写操作改为只读观察都会使原结果失效并保留审计记录。

## 3. 阶段门禁

### Gate 0：固定需求、系统和场景分母

1. 重新读取主文档和全部当前子表，保存 URL、revision、读取时间和文件 hash；无法重新取得的附件 revision 标为缺证据，不以旧导出推断当前内容。
2. 将 Test5 明确绑定到集团/GHR。本地 GHR 场景与 Beisen 跨系统需求分别标记；Beisen 在第二真实系统及单独授权到位前保持 blocked，并在之后的选定场景分母内。OEHR 未被单独纳入时不执行。
3. 人工审核需求流程、关键状态转换、角色交接、分支、字段和业务 Oracle，然后把经批准的场景清单固定到真实 Trial。当前 28 个本地 GHR 结果仍是规划候选；当前 180 条 BusinessScenario 均 blocked，二者都不能直接称为已冻结真实分母。
4. 保存范围版本、场景清单 hash、Oracle hash、目标系统、执行账号/角色断言、代码 commit 与 Trial ID。任何输入变化创建新 Trial，不覆写旧轮。

**通过条件：** 场景逐项有需求来源、起止状态、角色、前置条件、数据策略、系统绑定和可观察 Oracle；所有歧义经确认或继续 blocked；场景总数固定。

### Gate 1：候选工程与失败反例

针对每个包先运行对应失败反例，再跑全量测试、类型检查、构建、文档、浏览器夹具和包安装。反例失败意味着门禁有效；出现错误 `conform`、错误业务写入重放或错算指标则为阻断缺陷。

候选基线本轮已通过：141 个 Vitest 文件 / 1,178 个测试、TypeScript 检查、构建、文档构建、订单审批 Chromium 夹具 6/6、175 项 package contents 和新目录 package-install smoke。文档构建有既有大块警告。以上均是合入前候选证据，夹具结果为 synthetic。

### Gate 2：合入与包级实现验收

候选代码经审阅、CI 和合入后，以合入 commit 重跑受影响检查及包安装/宿主 smoke。每个交付包逐项对照第 4 节门槛；只有完整满足该包要求、证据归档且合入基线的包才记为 accepted。提交、推送、PR 或 CI 绿灯本身都不等于接受。不得因本地测试通过，把 `N/6` 提高。

### Gate 3：真实系统执行前置

只有以下条件同时成立，才允许建立 Trial 并开始业务写操作：

- 本轮 Test5 登录通过新上下文验证，且登录状态绑定到当前任务；不复用聊天凭据。
- GHR 场景与目标页面/唯一绑定、账号角色及各动作权限已有证据；用户对账号权限的声明作为授权上下文，不冒充系统观察到的角色授权记录。
- RequirementSet、Oracle、场景清单和固定分母已审核批准，EvaluationGate 不再有阻断项。
- 独立的目标系统后置查询和 TestData provider 已配置且只指向 Test5；查询返回多条时不任取首条。
- 写动作已获得任务授权；清理动作逐次提前通知并取得任务要求的通知确认。保留/关闭数据策略遵循用户批准方案。

任一条件未满足时只允许只读探索、候选需求分析和修复产品，不建 Trial、不写业务数据、不把手工改 Store 当作成功。

### Gate 4：三轮真实业务闭环

固定相同需求、系统、代码版本范围、场景分母和 Oracle，执行三轮独立 Trial。每轮使用新的 Trial ID 和本轮证据：

1. **首轮：** 验证需求分析、人工审核后的主流程 Oracle、数据创建/复用与业务列表后置查询。
2. **复用轮：** 从新会话恢复任务并复用已确认 System Brain 知识；核实运行版本、系统绑定、角色和业务实体引用仍一致。
3. **恢复轮：** 在创建、提交、转交、审批、关闭的发送前、发送后无响应和页面/进程中断点注入恢复；恢复先查业务后置状态，已完成则只对账，不重放写入。

每轮至少走过用户批准的本地 GHR 闭环：创建招聘需求 → 提交 → 转交审批 → 审批通过 → 关闭；具体选哪些分支由 Gate 0 清单决定。每项通过必须同时具备步骤证据与独立业务状态/关联副作用证据。失败、blocked、未执行、人工介入、产品修补、首次有效结果耗时、恢复结果与清理/保留结果全部入报告。

**禁止重复写入验收：** 故障注入后，创建实体数、提交次数、转交次数、审批次数与目标状态分别对账；任何重复业务写入为恢复失败，即使最后状态看似正确也不能通过。

### Gate 5：订单夹具与跨系统迁移

订单审批夹具验收角色交接、金额分支、拒绝、实体复用、延迟清理、重启恢复和业务规则不硬编码。当前 6/6 只能作为 synthetic 控制面证据。Beisen 的跨系统需求还需第二真实系统、单独授权、正式绑定和独立业务 Oracle；夹具通过不得替代第二系统迁移验收。

### Gate 6：复核与交付报告

以实际三轮数据生成报告：显示固定分母、真实完成分子、blocked/失败/未执行数、介入次数与原因、恢复成功率、业务验证率、清理成功率、样本量、未测量项、合成与真实隔离、与实测基线的变化、源码修补及外部依赖。由业务审核者复核主流程、状态转换、角色交接和异常分支标注，并从可执行故障集复核误报/漏检。

新目录安装需要验证安装、启动、Facade/CLI 身份、会话恢复、报告、加密鉴权材料隔离及宿主 smoke。发布 npm 仍需独立明确授权；本策略不包括发布。
