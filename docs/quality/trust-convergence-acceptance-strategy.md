# Brain Creator 已实施内容验收策略

版本：3.0
更新日期：2026-10-26
目的：先验收已经实施的 A–F 功能；发现具体缺陷时才进入修复。本文定义验收方法，不代表尚未执行的门禁已通过。

## 1. 本轮验收要回答什么

本轮检查候选分支中已经实现的功能，逐项回答：

1. 承诺的行为是否在产品代码中实现，并从真实产品入口可达？
2. 正常情况是否有正向结果，关键错误情况是否会被安全地拦截？
3. 测试、构建和运行证据是否绑定到被验收的准确代码版本？
4. 该功能目前只能在合成环境成立，还是已经在真实目标系统成立？

本轮重点是确认现有实现是否成立，不扩展无关功能，不以代码存在、测试数量或文档描述直接判通过。验收发现产品缺陷时，保留失败证据，修复后重跑原失败项和受影响回归。

## 3. 结论和计数必须分开

| 结论 | 统计对象 | 规则 |
|---|---|---|
| 候选实现验收 | 候选代码中通过本策略强制门禁的交付包 | 通过包数 `/6`；部分通过不计入通过数 |
| 正式交付验收 | 已合入选定基线且完成合入后冒烟的交付包 | 通过包数 `/6`；候选分支通过不能提前计入 |
| 真实业务完成度 | 固定范围内、由目标系统独立后置状态证明的场景 | 真实通过场景数 `/固定场景总数`；blocked、失败、未执行均保留在分母 |
| 自主完成度 | 无额外人工介入且真实通过的场景 | 符合条件场景数 `/同一固定场景总数`；初次授权/登录单列 |

合成浏览器、mock、历史截图及源码内模拟值只证明工程行为。不得将它们算入真实业务、自主完成、真实恢复或业务准确率。样本不足时写“未测量”，不得按零、通过或估算填报。

候选实现可在未合并时独立验收；本轮六包候选均通过，只能说明候选功能包验收完成。合并前正式交付计数仍为 `0/6`。真实业务验收另以 Trial 的独立业务证据判定。

## 4. 统一验收步骤

### 4.1 固定被验收版本

记录基线 SHA、候选产品代码 SHA、当前分支头、PR 状态、锁文件/包版本、工作区变更、Store schema、实际进程 build ID、MCP PID/启动时间、workspace 和 Provider。把功能证据绑到产品代码 SHA；文档更新提交的 CI 不能替代产品代码提交的功能测试。

### 4.2 建立逐条验收矩阵

将计划中的每条承诺拆成一条可观察行为，并记录：

| 字段 | 内容 |
|---|---|
| 包/条款 | A–F 及具体验收条款 |
| 产品实现 | 文件/服务/状态转换及对应 CLI、MCP、Facade、Runner 或宿主入口 |
| 正向证明 | 测试用例、实际输出和可复核产物 |
| 失败反例 | 应失败/阻塞的输入、操作和实际结果 |
| 运行身份 | 候选 SHA、Build ID、workspace、schema、Provider；未知字段注明 |
| 证据类型 | 单元、集成、浏览器夹具、包/宿主或真实系统 |
| 判定及缺口 | 通过、部分通过、未通过、阻塞、未执行或未测量 |

测试必须断言产品行为和结果；仅 mock 函数被调用、测试文件存在或 CI 配置存在，不构成行为证明。

### 4.3 先复核已有证据，再补缺口

逐条检查台账已有记录是否来自准确候选 SHA、是否有命令/退出码/测试数/原始产物、是否覆盖正向和失败路径。满足条件的证据复用；SHA 错位、只有摘要、缺失败反例或只测到内部 mock 的项目，标为缺证并补跑最小针对性检查。

产品代码或测试变化后，旧版本结果不能覆盖新版本。仅文档变化可以单独记录文档构建结果，但不能改变功能包判定。

### 4.4 先跑高风险失败反例

执行矩阵中最容易产生错误成功的反例；任何一个强制反例仍能得到错误成功，该包不得通过。修复后复跑原失败项、相关集成及受影响全量回归。不得删场景、改弱 Oracle、降低断言强度、跳过副作用或将失败归类成成功来通过门禁。

### 4.5 补齐适用的工程和产品入口检查

已有可复核证据且绑定准确版本的检查可复用。缺少或失效时，按改动范围补跑：定向测试、全量单元/集成套件、类型检查、构建、文档构建、包内容与新目录安装、浏览器夹具、CLI/MCP/Facade/Plugin/Skill/宿主 smoke、workspace 隔离、仓库卫生和对应 CI 矩阵。

真实系统脚本须先检查脚本副作用和当前授权。工程验收策略不等于真实业务写入或清理授权。

### 4.6 独立复核并归档

复核人按 SHA 和原始产物抽查结论，不能只读汇总表。报告中保留失败尝试、重跑原因、最终结果、人工介入和等待原因。报告与 PR 结论一致。

## 5. A–F 包验收矩阵

| 包 | 已实现内容要证明的行为 | 关键失败反例 | 通过门槛 |
|---|---|---|---|
| **A 运行身份与基线** | `doctor`、`bc_status`、CLI Runner、MCP 调度返回实际进程版本/commit/build ID、PID/启动时间、workspace、schema、Provider；未知身份明确显示未知；需求/代码变化不能复用旧 Trial；人工介入和恢复有归因；synthetic 与 real 隔离 | 磁盘代码已更新但 MCP 仍为旧进程；无 build identity 仍报 ready；输入变化后沿用旧 Trial；介入记录缺失；synthetic 进入真实分子 | 入口身份一致并指向进程；变化、未知和缺记录均 fail closed；Trial 记录及指标口径可追溯 |
| **B 证据与符合性** | 合同 ID、步骤 ID、运行、实体、Reporter、实际文件与 hash 精确绑定；图片可解码、trace 可读；Oracle 冻结；Conformance 分别说明适用性、证据充分性、实际业务值和比较结果；历史结果可重新评估且保留旧结论 | 错合同/错步骤/数组位置兜底；缺文件、替换/损坏文件或 Reporter 不一致；只有 `passed + strong` 就 conform；改预期、删断言、改语义后旧通过仍生效 | 每个强结果有可读、匹配且绑定准确的文件和结构化 Oracle；任一反例都不能晋升强信任或 conform |
| **C 路径与测试数据** | 从明确前置状态求到目标状态的唯一完整路径；角色、分支、副作用被保留；歧义需确认；跨用例实体引用和租约唯一；查询/创建/转换后验证再消费；清理或保留符合批准策略 | 共享来源选第一条流程；路径缺端点或有否定语义却生成正向步骤；多匹配取第一项；未验证就消费；无发送标记即重放；未通知先清理 | 路径歧义 fail closed；同一实体可追踪 lookup/create/transition/verify/consume/cleanup-or-retain；目标 Provider 的真实表现单独标记 |
| **D 连续推进与恢复** | 同一任务在新会话恢复；投影显示场景、角色、实体、步骤、页面、等待原因、下一步；写入保存 planned/sent/confirmed/reconciled；恢复前查询目标后置状态；报告持续更新 | 响应丢失导致重复创建/提交/审批；恢复到新 Trial/实体；凭进程存在声称窗口已可见；模拟查询冒充目标验证 | 合成故障回放证明不重复副作用；实际系统恢复只有在独立目标查询和真实运行后才算业务通过 |
| **E 真实业务评估** | 工程侧证明 Trial 门禁、固定分母、报告和订单审批控制夹具有效；业务侧在冻结需求/系统/场景/Oracle及授权后完成三轮独立 Trial；场景有独立后置状态证据 | 历史截图代替新结果；blocked/未执行从分母移除；没有独立查询就 conform；恢复重复写入；夹具结果称为真实系统通过 | 合成夹具仅判工程控制路径；真实结果按 Trial 单独判定。Test5 当前认证、场景/Oracle、后置检查及 Provider 未就绪时，真实验收阻塞；Beisen 等第二真实系统仍是外部依赖 |
| **F 复核与交付** | 真实/合成分开统计；提供样本量、分母、失败、阻塞、介入、恢复和清理结果；文档、包安装、启动、恢复、报告、宿主入口可用 | 无样本填零/通过；只报百分比不报原始计数；synthetic 混入真实指标；未经授权发布 | 工程交付证据可独立验收；没有真实样本的业务基线/准确率/自主率标“未测量”；npm 发布不自动执行 |

E 必须拆成“E-工程控制能力”和“E-真实业务结果”两条结论。真实 Trial 的外部前置不会否决 A–D 或 F 的工程验收；合成工程通过也不会让 E-真实业务通过。

## 6. 每包结论等级

| 状态 | 使用条件 |
|---|---|
| **通过** | 所有强制行为均有准确版本的正向证据、关键失败反例、必要入口/集成证据；无未关闭强制缺口 |
| **部分通过** | 已有部分行为和证据成立，但强制条款或证据链仍有缺口 |
| **未通过** | 发现实现违反条款，或失败反例被错误接受；待修复和重验 |
| **阻塞** | 只用于必须依赖外部系统、角色、鉴权、Provider 或批准信息才能运行的门槛；记录明确阻塞项 |
| **未执行** | 应执行的验收动作尚未运行；不能作为通过证据 |
| **未测量** | 没有符合口径的样本，无法计算指标；不等于 0 或通过 |

一个包只要有未解决的强制缺口，整体不能标“通过”。没有必要的真实环境时，只将真实业务子结论标为阻塞/未测量，不要把无关工程检查标成已通过。

## 7. 真实 Trial 的独立准入门

本节是 E-真实业务验收门，不阻止对已实现通用工程功能的静态审查和合成验收。执行 Test5/Beisen 写操作前，必须同时满足：

1. 固定需求及附件版本、候选代码身份、场景名单和场景分母。
2. 每个场景的前置状态、角色交接、目标状态、分支、业务实体及 Oracle 已审核。
3. 本轮鉴权、系统路由和实际操作权限得到验证；不能从登录或菜单可见推断权限。
4. 正确 `systemId` 下的目标 TestData Provider 与独立只读后置查询可用。
5. 创建、提交、转交、审批、关闭以及清理/保留范围符合已授权策略；清理前按约定通知。
6. 每轮保存 Trial ID、需求/Oracle hash、构建身份、实体引用、操作状态、证据 hash、人工介入及最终清理/保留结果。
7. 中断后先检查目标状态；已生效操作只核对，不重复发送。

Test5 本地 GHR 与 Beisen 跨系统场景分开报告。第二真实系统及单独授权到位前，Beisen 真实场景保持 blocked；订单审批夹具不能替代迁移验收。冻结分母后，blocked、失败和未执行场景均保留。

## 8. 验收报告必备内容

1. 基线 SHA、候选产品代码 SHA、当前分支头、PR 状态、包/运行身份及证据归档位置。
2. A–F 每包逐条矩阵：承诺、实现入口、正向证据、失败反例、准确版本、结论、未完成项、复核人。
3. 候选工程通过数 `/6`、正式交付通过数 `/6`；不能用一个数字混报。
4. 真实业务与自主完成的分子、固定分母和原始场景数；blocked、失败、未执行、人工介入、恢复和清理分别列出。
5. 合成证据单列；缺少真实数据的指标写“未测量”；外部依赖及所需输入明确列出。
6. 缺陷的复现条件、修复 SHA、原失败及复验结果；发布状态和授权状态。

## 9. 本轮执行顺序

1. 复核实际候选代码 SHA 与现有台账，确认已有证据是否可复用。
2. 按 A–F 建立逐条矩阵，先针对证据真实性、歧义路径、实体/租约唯一性、恢复不重放等高风险反例。
3. 对缺失或版本不匹配的检查补跑最小定向验收；若发现代码缺陷，修复并重新冻结候选 SHA。
4. 对最终准确候选 SHA 补齐全量工程套件、构建、文档、包安装及适用宿主/浏览器 smoke 和 CI。
5. 逐包签署候选结论；不能以“仓库实现很多”或“多数测试绿灯”替代强制条款逐项通过。
6. 候选通过后，合并到选定基线，再做安装、身份、入口及恢复的合入后 smoke，更新正式 `/6`。
7. E-真实业务等待其准入门满足后单独执行；npm 发布仍需明确授权。
