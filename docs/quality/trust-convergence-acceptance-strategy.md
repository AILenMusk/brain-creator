## 1. 本次验收要回答的问题

验收重点是判断已提交的 A–F 实施内容是否满足各自的交付条件，并说明哪些结论只由合成测试支持、哪些已经在真实业务系统验证。以下三件事必须分开报告：

1. **候选实现有工程证据**：某一准确 commit 上的代码审查、反例测试和集成检查通过。
2. **交付包正式验收**：候选证据齐全，代码合入选定基线，并通过合入后的身份和安装冒烟检查。
3. **真实业务场景通过**：在授权系统中执行，且由独立的目标系统后置状态和有效证据证明符合已批准 Oracle。

代码存在、单测通过、CI 绿色、PR 合入、浏览器夹具通过都不能单独替代另外两种结论。

### 本轮验收策略

本轮优先验收已经实施的 A–F 功能，不扩展需求范围，也不把真实 Trial 当作全部工程验收的前置条件。先对每项已实施能力核对“验收条款—代码行为—正向用例—失败反例—集成/宿主检查—版本身份”，按包给出候选结论；真实业务 Trial 单列准入，只有 E 的真实业务部分和业务指标因此保持阻塞/未测量。

验收分三道门：

1. **本地工作树验收**：可接受准确工作树上的测试和 smoke 证据；任何未提交代码均标为 dirty，不能声称远程 CI 已覆盖。
2. **候选版本验收**：提交后对该 commit 重跑必要失败反例、完整工程门禁并核验远程 CI；证据齐备后才可标为“候选工程通过”。
3. **正式包与真实业务验收**：合入后重验运行身份、安装和宿主入口，才计入 `N/6`；真实业务必须再通过目标系统独立后置状态核对。

任何门禁失败都保留原始失败记录；定位和修复后重跑同一反例及受影响的完整门禁，不通过调低断言、删除样本或复用旧运行结果消除失败。

## 4. 验收证据链

每条实施声明必须建立一条可复核记录：

> 计划要求 → 代码位置/关键行为 → 正向测试 → 失败反例 → 准确 commit/build → 命令或 CI 结果 → 产物位置 → 验收结论

验收时按以下顺序执行：

1. **冻结版本和范围**：记录主线与候选 SHA、PR、依赖锁文件、Store schema、包版本、构建标识、MCP PID/启动时间、workspace、Provider，以及需求/系统/场景/Oracle 的 revision 或 hash。变化即创建新验证记录，不覆盖旧记录。
2. **先审失败反例**：证明错误输入和不完整证据不能产生“强通过”“conform”或可信晋升。反例失败即停止对应包的通过判定。
3. **审查实现声明**：代码路径与产品要求一一对应；只看文件存在、测试名称或 mock 调用不构成证据。
4. **运行包级和集成检查**：所有结果绑定到准确 commit。代码变化后重跑受影响测试和完整候选检查；旧 commit 的绿灯不能替代新 commit 检查。
5. **失败归因与复验**：区分产品行为错误、测试夹具/运行环境问题和外部阻塞；修复不得弱化预期，原失败与复验结果都归档。
6. **独立复核与归档**：复核人依据命令输出、CI 链接、日志、报告和产物可重现结论。浏览器夹具明确标注 synthetic。
7. **合入后正式判定**：只有合入选定基线并完成合入后身份、安装和宿主冒烟，包才计入 `N/6`。
8. **另行运行真实 Trial**：只有真实 Trial 前置条件全部满足才执行业务写入，并用目标系统独立查询验证结果。
