# Brain Creator 实施内容验收策略

更新日期：2026-10-26

## 1. 本轮验收目标

本策略用于验收已实施的 A–F 六个交付包。重点是逐项证明“代码实现了什么、反例是否被拦截、运行证据是否可信、哪些能力仍未在真实系统验证”。代码存在、测试通过、PR 合入和真实业务完成是不同结论，不能互相代替。

本轮代码基线为 `origin/main` `62d7487`（PR #185）。候选实现位于 `codex/trust-closure-main`、PR #186；此前远程分支头为 `4f45319`。本次 C 包目标查询校验改动仍在工作树，尚未形成新的远程 commit。已核实的上一候选 CI 为代码 run 473（`fde5723`，Node 20/22 通过）和文档 run 184（`ffb0009` 通过）；它们不覆盖本次 C 包改动。PR 尚未合入。

## 2. 结论和计数规则

每项验收使用以下状态：

| 状态 | 判定 |
| --- | --- |
| 通过 | 必须证据齐全、反例通过，且结果对应被验收的准确 commit/build。 |
| 部分通过 | 已实现并有候选工程证据，但仍缺明确门禁或集成条件。 |
| 未通过 | 发现违反验收条件的实现或反例能产生错误成功。修复后以新 commit 重验。 |
| 阻塞 | 前置条件或外部依赖缺失，当前无法安全执行。 |
| 未测量 | 没有足够实测数据计算指标；不得改记为 0 或通过。 |

验收报告分开显示三项：

- **实现完成度：** 满足包级门槛、证据归档并合入选定基线的交付包数 `/ 6`。合入前只记“候选通过”，不增加 `N/6`。
- **真实业务完成度：** 有符合已批准 Oracle 的独立业务后置证据的场景数 `/ 冻结的全部选定场景数`。失败、blocked、未执行均留在分母。
- **自主完成度：** 无额外人工操作且真实符合的场景数 `/ 同一固定分母`。初始授权/登录单独统计；后续每次人工介入均记录原因。

无 Trial 或样本不足时，真实业务完成度、自主完成度、恢复率、清理率和基线变化均标为“未测量”。合成夹具单列，不进入真实指标。

## 3. 验收执行顺序

### 阶段 0：固定被验收版本

记录 `origin/main`、候选分支、PR、准确 commit、构建身份、工作区状态、依赖锁文件和 Store schema。需求输入记录主文档及子文档 revision、文件 hash；每轮实测再绑定 `systemId`、`knowledgeProjectId`、Trial ID、场景清单 hash 和 Oracle hash。任何代码、需求、系统绑定或场景变化都建立新的候选验证或 Trial，不覆盖旧结果。

### 阶段 1：逐包追踪实现声明

每条声明必须能追到：需求/技术约束 → 实现文件和关键分支 → 正向测试 → 失败反例 → 本次运行结果。测试应验证用户可观察的结果，不只检查内部字段被写入。对有副作用的动作，复核是否会创建、提交、转交、审批或清理真实业务数据。

### 阶段 2：先跑失败反例

先验证错误输入或伪造证据不能获得成功，再跑正向回归。必须覆盖：合同/步骤错配、缺失或被替换的产物、改变 Oracle 或删除断言、歧义路径/数据多匹配、创建无后置验证、发送后中断、重复恢复、blocked 场景被移出分母、synthetic 混入真实统计。任何错误 `conform`、无证据可信晋升或重复业务写入均阻断相关包。

### 阶段 3：工程验证候选 commit

对受影响包跑定向反例和单测，再对完整候选 commit 跑：

```text
npm test
npx tsc --noEmit
npm run build
npm run docs:build
npm run verify:package-contents
npm run verify:package-install
npm run verify:order-fixture
```

同时检查 PR CI、仓库卫生和宿主 smoke。所有日志、包清单、安装目录、构建身份和浏览器夹具产物都注明 commit。若代码发生变化，旧 commit 的绿灯不能替代新 commit 的检查。CI 绿灯只证明该流水线中的门禁通过，不自动等于包验收。

### 阶段 4：逐包作出验收决定

逐项按第 4 节门槛记录状态、证据、反例结果和未满足条件。只有包内所有必需条件满足、复核人能复现结论、结果已归档且代码合入指定基线，才将该包计入 `N/6`。部分通过和阻塞项不能按估算折算成比例。

### 阶段 5：单独验收真实业务

只有正式需求、场景和 Oracle 已审核冻结，系统唯一绑定、当前鉴权、动作权限、独立目标后置查询和 TestData provider 均就绪，才开始 Test5 Trial。每次清理前通知并记录确认。完成三轮独立 Trial：首次执行、知识复用、新会话/进程中断恢复。恢复前先查目标系统状态；若目标动作已生效，只对账，不重放写入。Beisen 保留为第二真实系统外部依赖，未提供系统及单独授权前保持 blocked。

## 6. 真实 Trial 启动条件

正式需求源当前记录为主文档 revision `2045`；五份附件分析可作为草稿输入，不自动成为业务 Oracle。真实 Trial 启动前必须完成：

1. 审核并固定每个选定场景的需求来源、起止状态、角色交接、前置条件、数据策略、系统绑定、步骤和 Oracle。
2. 对本地 Test5 GHR 场景冻结固定分母；Beisen 场景列入范围但在第二真实系统与单独授权到位前保持 blocked，不以排除方式减少分母。
3. 取得并验证本轮有效登录上下文，确认目标路由、唯一绑定、角色与动作权限；用户授权作为边界记录，不能代替系统观察到的角色权限证据。
4. 配置只指向 Test5 的业务后置查询和数据生命周期验证。创建/提交/转交/审批/关闭按当前授权执行；清理必须提前通知。
5. 固定 Trial ID、需求/场景/Oracle hash、代码/build identity、系统、账号角色断言和运行产物。发生源码修补时重建候选验证；发生需求/系统/场景变更时创建新 Trial。

任一条件未满足，结果记录为阻塞或未测量，不开始业务写入，不手工改 Store 伪造成功。

## 7. 最终验收报告格式

最终交付必须包含：

- 精确基线、候选/合入 commit、PR、构建身份和检查链接。
- A–F 每包状态、实现文件、关键正反例、运行输出、证据位置、复核人和未满足门槛。
- `N/6` 实现完成度，以及真实业务、自主完成度的分子/分母/原始场景数；缺测项标“未测量”。
- 每轮 Trial 的需求 revision、场景清单和 Oracle hash、运行版本、系统实体引用、后置状态、介入记录、失败、恢复和清理/保留结果。
- 独立列出的 synthetic 结果、失败与 blocked 场景、未验证范围、第二真实系统依赖及 npm 未发布状态。

通过六包验收仅表示本轮交付完成，不据此宣称任意系统零准备自主测试、第二真实系统迁移、生产 Runner 长期稳定或跨行业泛化已完成。
