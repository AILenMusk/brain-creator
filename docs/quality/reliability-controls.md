# Reliability controls

Brain Creator now treats reliability as a control plane instead of a claim that a green run proves the whole requirement.

## Cross-surface recovery

System exploration records the requested surface (`document`, `iframe`, `popup`, `shadow-root`, or `wujie`) and reacquires that surface independently. A missing child surface is not replaced with the main document. Cross-origin or unregistered surfaces are blocked with evidence so the caller can create a Gap.

## Authentication refresh

Authentication refresh uses a provider registry and one common adapter contract. Token and cookie profiles can be re-materialized into an encrypted-at-rest browser state by the built-in adapter; browser contexts receive the decrypted state in memory. Legacy plaintext state files are encrypted on first read. OAuth uses the standard refresh-token grant and persists rotated refresh tokens only in the encrypted AuthProfile, CAS validates a configured service ticket and then requires a target-system session exchange, and SAML prefers a session cookie returned by the configured endpoint before falling back to a session token. The host-agent adapter remains available for browser-specific or vendor-specific flows. Provider credentials and endpoints are supplied through the encrypted AuthProfile; no vendor secret is bundled in Brain Creator. Refresh attempts have a bounded timeout and never return raw secrets. A successful CAS validation without a target session is a failed refresh, not a usable browser state.

Use `brain-creator auth capture --system <id> --profile <id>` to open an isolated visible browser for user-operated login. It enforces the system origin allowlist, encrypts the captured state before writing it, and verifies it in a fresh browser context before marking the profile verified. Credentials are not entered in the CLI or chat.

Use `bc_configure` with `target=auth` and `operation=preflight` to check provider readiness without refreshing credentials, then use `operation=refresh` to request a refresh explicitly. `bc_status` reports registered, configured, and unavailable refresh providers so a host can preflight an OAuth/CAS/SAML profile before a suite waits on it. A provider-specific adapter may implement deeper checks; a registered adapter without a preflight hook is reported as registered-only readiness, not as a successful login.

Requirement Suite execution applies the same readiness gate before creating an execution plan when the selected profile declares a refresh provider or uses token/cookie materialization. A missing or unavailable provider creates one open `requirement-suite-auth-preflight` Gap for the run and prevents the case from entering the Agent/Playwright chain. Manual script profiles without a declared refresh provider continue through the existing verified-browser-state path.

## Same-system requirement reconciliation

Requirement suites persist the expected requirement-set scope and reconcile executable cases before and during review. The result distinguishes:

- `complete`: every expected requirement set has current cases and no cross-system or duplicate compile-key reference.
- `partial`: a requirement set or executable case is missing.
- `conflicted`: a case belongs to another system or duplicate current compile keys exist.

The reconciliation is visible from `bc_review` with `target=requirement-suite-run`. It also reports missing TestIntents, missing executable cases, superseded revisions, and unbound cases for the same knowledge project.

## Long-cycle stability

Stability is evaluated with target and minimum sample counts, failure rate, consecutive failures, maximum duration, strong evidence, and blocked-run policy. The result includes threshold diagnostics, not only a verdict, so a report can distinguish insufficient sample from an exceeded failure, duration, evidence, or blocked-run threshold. A single green run remains `insufficient-sample`. When a minimum interval is configured, the next iteration is persisted with `nextRunAt` and is not started early.

Scheduled stability runs use an explicit claim/lease control plane. An external scheduler or host Agent can preview due work through `bc_status`, use `suiteAction=claim-next-scheduled` to claim work, or use `suiteAction=process-next-scheduled` to claim and process one due iteration with bounded one-at-a-time execution. The consolidated CLI also accepts `--max-wall-time-ms` and `--lease-renewal-ms`; long runs renew the lease in the background, stop before starting another case when the wall-clock budget is exhausted, and report duration and renewal count. It can release a lease with an error and bounded exponential backoff for retry. The status facade exposes bounded per-run `scheduledRuns` records with the run ID, project ownership, due state, iteration target, lease expiry, and last scheduler error, so a scheduler can enumerate concrete work before claiming it. An expired lease can be claimed by another owner, so a crashed process does not permanently strand the run. The scheduler remains externally triggered, which keeps the local MVP deterministic and avoids an unbounded background worker inside MCP.

The repository includes a GitHub Actions scheduler fixture in `.github/workflows/brain-creator-runner.yml`. It runs every 15 minutes or by manual dispatch, restores the previous sharded store from a short-lived Runner state artifact, processes at most one due iteration, and uploads the updated state and report. The workflow uses a concurrency group so only one writer can advance the fixture. The fixture is synthetic evidence for lease, recovery, and multi-run stability behavior; production deployments should replace Artifact state with an approved external store and keep the same claim/renew/release contract.

## Target postcondition verifier

The production MCP context can load an explicitly configured target adapter from `BRAIN_CREATOR_POSTCONDITION_VERIFIER_MODULE`, relative to the Brain Creator workspace. The module must be reviewed trusted code inside that workspace and export an async `verifyPostcondition(input)` function (or a default function) implementing `ExecutionPostconditionVerifier`. It receives the immutable system/action/entity/postcondition binding and must query the target system independently; a confirmed response must include actual result, check time, evidence references, and a hash-bound `.brain-creator/` JSON artifact of type `execution-postcondition-observation` matching the supplied binding. A missing, out-of-workspace, malformed, or throwing adapter returns `unavailable`; it never promotes the pending action. Without this explicit target-specific adapter, automatic reconciliation remains unavailable and requires verified manual recovery evidence. Loading this module executes its code in the MCP process, so enabling it is a trusted local-code decision, not a credential or business-write authorization.

`bc_status` exposes `recoveryCapabilities.automaticPostconditionVerification` as `configured` or `not-configured`, so a pending write's recovery path can be reviewed before automatic reconciliation is attempted. `configured` only reports that an adapter is present; target access and evidence validity are established only by a successful operation-specific query and artifact validation.

## Execution visibility

Every Run Ledger entry receives a stable per-run sequence and projects to an `ExecutionProgressEvent`. Reporter-backed steps add step ID, title, assertion summary, screenshot, elapsed time, and trace identity. Protected values and URL query values are redacted before persistence.

Trial recovery metrics identify each action's terminal reconciliation event by Run Ledger sequence, with timestamp and ID as legacy tie-breakers. Equal timestamps cannot make a successful recovery appear unresolved or turn an earlier pending event into the terminal result.

Recovery reconciles two durable layers: the persisted Suite state is authoritative for the run terminal status and current case, while the Run Ledger supplies step-level progress and evidence details. If a process stops after the Suite state is written but before the final Ledger event, `bc_status` reports the Suite result and marks the recovery as reconciled instead of replaying a stale step. If no Ledger exists yet, status recovery still reports the persisted waiting case and next action; if only Ledger data exists, the response identifies that it is ledger-only evidence.

`bc_run` and `bc_submit_agent_output` emit MCP Progress Notifications when the caller supplies a progress token. Notification delivery is best-effort and never changes the execution outcome; the persisted Suite state and Run Ledger are reconciled during recovery. `bc_status` reports the current event and a `possiblyStalled` warning after the active event exceeds the configured threshold. Terminal events are never marked stalled. The static Suite report is rewritten after each completed case so an operator can inspect progress and evidence before the whole Suite ends.

When a caller status disagrees with a structured Playwright Reporter result, a non-passing Reporter result wins over a requested `passed` status and the disagreement is retained as an evidence warning. This prevents a green caller path from masking a failed or blocked execution.

Execution has an explicit `browserMode=headless|observe` contract. Headless remains the unattended default. Observe mode adds Playwright `--headed`, preserves one worker, is persisted on the Suite/Agent task, and is displayed by status and the static report. A desktop capability check fails closed when a window cannot be shown; there is no hidden fallback. Browser visibility improves operator confidence but never changes assertion assurance or replaces structured evidence.

When Brain Creator starts `npx playwright` for a run, it resolves the Playwright CLI from that run's `workDir` first, then falls back to the Brain Creator installation. The generated seed and test therefore use the same workspace-installed `@playwright/test` runtime as the CLI, avoiding duplicate Playwright test registries in isolated business projects.

Interrupted write reconciliation is bound to the original Run Ledger action. Reconciliation requires an unresolved `sent` or `reconciliation-required` entry and rejects a changed system/case binding, action semantic, postcondition, or entity reference. Both automatic and manual artifact validators require exactly one suite-run identity, rejecting empty or contradictory run bindings. Automatic verification inherits the stored entity reference and validates its structured, hash-bound observation against that original action, so a recovery request cannot substitute a weaker Oracle after the write was sent.

The write-send marker also requires a frozen postcondition. A planned action carries its semantic, target entity, and postcondition forward to `sent`; changing them or sending without a postcondition is rejected. This ensures the recovery Oracle exists before the external write, rather than being introduced only after an uncertain result.

Created-entity cleanup tasks include an advance-notice message and its SHA-256. The Host Agent must deliver the notice, call `bc_prepare action=confirm-cleanup-notice` with that digest, then mark the task sent; `mark-test-data-sent` rejects cleanup without the acknowledgment. If read-only reconciliation proves cleanup did not apply, the acknowledgment is cleared so a retry requires a fresh notice. The stored digest/timestamp records the Host Agent's acknowledgment; it does not independently prove that the user saw the message.

Manual reconciliation is also evidence-gated: the caller must identify an operator and provide at least one readable artifact under `.brain-creator/` with its expected SHA-256, in addition to non-secret evidence references. JSON observations must be `manual-execution-postcondition-observation` records bound to the exact suite run, system, action, entity, postcondition, actual result, check time, and operator; screenshots must decode and trace ZIPs must contain readable events. The verified artifact path/hash is stored on the reconciled Run Ledger entry and attached to any Trial intervention record. Evidence references alone do not authorize continuation.

The MCP runtime signs Run Ledger entries with the workspace integrity key and chains them in per-run sequence. Trial review revalidates current action-artifact hashes, the HMAC chain, and the signed terminal event for completed/failed/blocked/cancelled runs. Missing, reordered, unsigned legacy, or modified entries cannot support a recovery-success metric; the entries remain available for audit. This authenticates the local record, not the continued availability or correctness of the external target system.

The terminal Requirement Suite report includes the latest Run Ledger phase per write action, its immutable semantic/entity/postcondition, references, and hash-bound artifact links. It labels these as audit evidence, not a conformance verdict; conformance remains based on the separately validated execution evidence and Oracle.

Business Oracle applicability is explicit. Unconditional Oracle contracts state that no branch condition applies; conditional contracts enumerate source-backed conditions, and the Reporter must return each actual condition value with evidence references that resolve to validated files. Conformance compares those values against the condition operators instead of trusting a Boolean applicability label. Expectation and applicability references must belong to the contract, the execution evidence ID must appear in the execution references, and an Oracle entity reference must match the Reporter entity. Legacy Boolean-only applicability records remain reviewable but cannot produce a new `conform` result.

Execution provenance is declared on the selected `SystemProfile` through `executionProvenance`; it defaults to `unknown` and is snapshotted into evidence at run creation. Completion/report payloads cannot promote a run by supplying a provenance label. Local fixtures must be configured as `synthetic`, and only explicitly classified business systems can produce `real-system` conformance; this classification does not replace baseline approval, evidence validation, or independent business postconditions.

Document Suite actions that participate in an Evaluation Trial should be recorded with `evaluationTrialId` and, when known, `businessScenarioId`. If a manual recovery was not bound at action start, reconciliation auto-binds only when exactly one active Trial matches the system; multiple matching Trials require an explicit Trial ID. Trial review detects bound manual recovery events without intervention records, and a bound scenario must remain in the frozen scope.
